# Repository guidance

- Read `PLAN.md` before choosing work or preparing a release. Checked tasks mean implemented on `main`; experimental prototypes are not completed work or a commitment to ship. Frozen ideas stay outside releases.
- `extension/README.md` is Store-facing marketing/user documentation: describe benefits and usage, not implementation details such as caching internals. Keep technical decisions in `PLAN.md` or code.

## Development and verification

- Only `extension/` is submitted to the Raycast Store. `tests/` is a separate npm package importing `extension/src`; install extension dependencies before test dependencies.
- Root npm scripts wrap the two packages and run `npm install` on each invocation. For checks without reinstalling:
  - In `extension/`: `npm run lint`, `npx tsc --noEmit`, `npm run build`.
  - In `tests/`: `npm test`; focused: `npm test -- 2do.test.ts -t "saveTask"`.
- `npm run dev` in `extension/` loads the extension into Raycast; it is not a browser app.
- `raycast-env.d.ts` is generated by Raycast and ignored by git; change `extension/package.json` for commands/preferences rather than editing generated types.
- Unit tests must mock `@raycast/utils` so `runAppleScript` never touches real 2Do. Preserve the alias in `tests/vitest.config.ts`: mocks and extension imports must resolve to the same module. Mock `@raycast/api` too; it has no standalone runtime outside Raycast.
- For lint failures, follow `.claude/skills/fix-lint/SKILL.md`; asset/account failures may require the user rather than code changes.

## Releases

- **`main`** holds what's in the Raycast Store, plus the release being prepared. Store PRs are published from `main`.
- **`experimental`** holds earlier unreleased work to draw from selectively; it also contains frozen features.
- **Sizing rule:** if it's too much for a human reviewer to parse, it needs to be smaller.
- **Docs:** `PLAN.md`'s Releases section lists what's released and the order of the next releases.

### Preparing a release, on `main`

1. In `extension/`, run `npx ray pull-contributions` first to bring in Store-repo edits. Record the pre-pull HEAD. It may re-pull edits already present; if the merge changes no files, undo only that pull's commits and delete only its new `contributions/merge-*` branch, preserving pre-existing work.
2. Take the next release in `PLAN.md`'s order, checked against the sizing rule. Build it as one commit (drawing from `experimental`'s version of the files where it exists, leaving out code for later releases). Keep the diff small: avoid re-indenting unchanged code.
3. Edit `extension/CHANGELOG.md` to describe exactly this release: one new `## [Title] - {PR_MERGE_DATE}` section above the released ones. Check `extension/README.md` describes only what ships.
4. Done when lint and build pass in `extension/` and `npm test` passes in `tests/`. Then publish with `npm run publish` in `extension/`. Fixes from the Store review go on `main` as their own commits.
5. In `PLAN.md`'s Releases section, move the release to Released with its PR link, and its date once merged.
